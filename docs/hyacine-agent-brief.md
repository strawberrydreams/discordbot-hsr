## 1. 프로젝트 현황 (README 기준, 코드로 검증할 것)

- Python 3.12+, discord.py, SQLite
- Docker Compose 운영 (`bot` + `backup` 서비스, 동일 이미지, non-root `bot` UID)
- macOS LaunchAgent 대체 경로 존재 (`deploy/macos`)
- 설정은 `settings/*.json` (persona, forbidden_words, games), 비밀값은 `.env.secrets`, 런타임 설정은 `.env.runtime`
- 데이터는 `guild_id`로 서버별 분리. 예외: AI 사용 한도만 사용자별로 봇 인스턴스 전역 공유
- 슬래시 명령은 전역 등록, 명령어는 한국어
- privileged intent 사용 중: Message Content(금지어), Server Members(퇴장 시 파티 정리)
- 선택적 로컬 웹 관리 (`ADMIN_TOKEN`, `127.0.0.1:8080` 고정)
- 봇이 서버에서 나가면 해당 서버 데이터 자동 삭제
- MIT 라이선스, 외부 기여 미수용

## 4. 설계 원칙

1. **단순함이 확장성보다 우선한다.** 30명이다.
2. **의존성 추가는 비용이다.** 셀프호스터가 설치해야 할 것이 늘어나면 채택률이 떨어진다. 새 런타임 의존성(DB 서버, 캐시 서버, 별도 프로세스)을 추가하려면 그 이유를 명시적으로 정당화하라.
3. **선택 기능은 없으면 우아하게 비활성.** 저장소에 이미 좋은 선례가 있다: `PyNaCl`/`yt-dlp`가 없으면 음악 extension만 건너뛰고 나머지는 계속 동작한다. 새 기능도 이 패턴을 따른다.
4. **되돌리기 쉬운 선택을 우선한다.** 확신이 없으면 더 검증 가능하고 더 가역적인 쪽.

### 6.2 금지어 필터 — 의도 명확화 (중요)

**이 기능은 제재 기능이 아니다.** 메시지를 차단하거나 사용자를 처벌하기 위한 것이 아니라, 누가 어떤 금지어를 썼는지 공개적으로 한 번 더 언급해 "박제"하는 것이 의도된 동작이다. 실제 응답 형태:

```python
f"🛑🛑 {message.author.mention} 삐삑~~ 나쁜 단어 **{bad_word}** 금지! 금지! 🛑🛑"
```

따라서:

- 원본 메시지는 **삭제하지 않는다.** 그대로 둔다.
- 어떤 단어가 걸렸는지 **응답에 그대로 노출한다.** 이게 기능의 핵심이다.
- 작성자를 멘션한다. 알림이 가는 것이 의도된 동작이다.
- 길드별 경고 횟수 집계는 현행 유지.
- Message Content intent는 **필수**다. 어떤 단어가 매칭됐는지 알아야 하므로 제거할 수 없다.

**이 설계 때문에 반드시 처리해야 할 기술 요구사항:**

1. **봇·웹훅 메시지 무시 (최우선).** 봇의 박제 응답 자체가 금지어를 포함한다. 작성자 체크가 없으면 **자기 응답에 다시 반응해 무한 루프**가 된다. 같은 길드에 이 봇의 인스턴스가 둘 이상 있으면 서로를 트리거하는 핑퐁 루프도 발생한다. `message.author.bot` 체크는 협상 불가.
2. **채널당 응답 쿨다운.** 누군가 금지어를 20번 연속 입력하면 봇 응답 20개가 생긴다. 채널 메시지 버킷은 5개/5초다. 채널·사용자 단위 쿨다운 또는 합치기(coalescing)가 필요하다.
3. **`allowed_mentions` 명시적 설정.** 멘션 알림이 의도된 동작이므로 켜되, 라이브러리 기본값에 의존하지 말고 명시하라. 셀프호스터가 알림만 끌 수 있는 옵션을 제공하라.
4. **응답 템플릿을 설정으로 분리.** 위 문구는 한국어이고 이 봇의 캐릭터에 맞춰진 것이다. 저장소가 공개 배포되므로 `settings/`에서 템플릿을 바꿀 수 있어야 한다.
5. **길드별 on/off.** `/설정`에 토글을 추가하라.
6. **매칭 정책 결정.** 한국어는 조사가 붙어 부분 일치가 필요하지만, 그만큼 오탐이 늘어난다(무해한 단어가 금지어를 부분 문자열로 포함하는 경우). 현재 코드의 매칭 방식을 확인하고, 필요하면 허용 목록(allow list)을 추가하라.
7. **README에 동작 명시.** 이 기능이 "금지어를 공개적으로 다시 언급하고 작성자를 멘션한다"는 점을 문서화하라. 30명 지인 서버에서는 농담이지만, 모르는 사람의 서버에서는 괴롭힘 증폭 수단이 될 수 있다. 동작을 바꾸라는 뜻이 아니라, 셀프호스터가 알고 켜도록 문서화하라는 뜻이다.

### 6.3 유지

| 기능 | 지시 |
|---|---|
| 파티 모집 패널 | 현행 유지. `settings/games.json` 기반 게임별 영속 패널. **선택 개선**: "게임·역할 설정 변경 후 봇 재시작 필요"를 재시작 없는 리로드로 바꿀 수 있는지 검토하고, 비용이 크면 하지 말 것 |
| 이벤트 (`/이벤트`) | 현행 유지 |
| 인사 | 현행 유지. 코드에서 실제 구현 위치를 먼저 찾을 것 (README 기능 목록에 없음) |
| AI 대화 / 이미지 | 현행 유지. 사용자별 KST 일일 한도(`LIMIT_LIGHT`, `LIMIT_DEEP`, `LIMIT_IMAGE`) 유지. **키가 없으면 해당 명령만 비활성**하고 봇은 정상 기동할 것 |

AI 한도의 다중 서버 동작: 현재 한도는 "같은 봇 인스턴스 안에서 모든 Guild에 걸쳐 사용자별로 공유"된다. 셀프호스터의 API 비용이 걸린 문제이므로 인스턴스 전역이 맞다. 유지하라.

### 6.4 추가 — 캐릭터/프로필 카드 + UID 등록

계정 연동은 별도 기능이 아니라 이 기능의 일부다. OAuth 없이 구현한다.

**명령**

- `/등록 <UID>` — Discord 사용자와 게임 UID를 매핑
- `/등록해제` — 매핑 삭제
- 카드 표시 명령 (이름은 기존 명령 체계에 맞춰 결정)

**데이터 소스**

- Enka.Network. UID 기반, 인증 불필요
- Python 래퍼 `enka-py`가 GI/HSR/ZZZ를 지원하며 SQLite 캐싱과 HSR 스탯 계산을 포함한다. 먼저 이걸 평가하라

**필수 기술 요구**

1. **진열장 미설정 케이스 처리 (최우선 UX 이슈).** Enka는 **인게임 "캐릭터 진열장"에 올려둔 캐릭터만** 반환한다. 진열장을 설정하지 않은 사용자는 UID가 유효해도 캐릭터 데이터가 비어 있다. 이게 Enka 기반 봇의 1순위 문의 사항이다. "데이터 없음" 대신 게임 내에서 진열장을 설정하는 방법을 안내하는 메시지를 반환하라.
2. **UID 유효성 검증**을 등록 시점에 수행하라. 잘못된 UID를 저장한 뒤 카드 명령에서 실패하게 두지 마라.
3. **`defer` 필수.** 명령 핸들러 첫 동작은 `await interaction.response.defer()`.
4. **이미지 합성은 `asyncio.to_thread` 또는 executor로 오프로드.** Pillow는 이벤트 루프를 블로킹한다.
5. **UID당 응답 캐싱** (최소 수 분). 진열장 데이터는 자주 바뀌지 않고, 공용 API에 부담을 주지 않는 것이 예의다.
6. **외부 API 실패 처리.** 타임아웃 + 사용자 친화적 실패 메시지. 최소한 연속 실패 시 백오프.
7. **에셋 라이선스 확인.** 폰트·캐릭터 이미지·아이콘을 저장소에 번들할 수 있는지, 번들 시 저장소 크기가 어떻게 되는지 검토하고 보고하라.

**UID 매핑의 저장 범위 — 결정 후 진행**

기존 불변식은 "모든 데이터는 `guild_id` 파티션, 예외는 AI 한도뿐"이다. UID는 사용자당 하나이므로 길드별로 저장하면 같은 사람이 서버마다 다시 등록해야 한다.

- **권장**: AI 한도와 같은 취급 — 봇 인스턴스 내 **사용자별 전역**. 두 번째 명시적 예외로 문서화
- 이 경우 "길드 이탈 시 데이터 삭제" 규칙과 충돌한다. 한 서버를 나갔다고 UID 매핑을 지우면 안 된다. **삭제 규칙을 명시적으로 정의하고 README에 기록하라**

이 항목은 사용자에게 확인 후 진행하라.

1. **인벤토리**: 저장소를 읽고, 각 기능이 어느 모듈·테이블·설정에 걸쳐 있는지 매핑한다. 삭제 대상의 실제 결합도를 확인한다.
2. **§7 확정**: 질문하고 답을 받는다.
3. **삭제 먼저**: 출석/포인트, 주가, 음악. 표면적을 줄인 상태에서 나머지를 작업하는 게 훨씬 안전하다. 각 삭제는 독립적으로 커밋하고 테스트가 통과해야 한다.
4. **저장소 계층 추상화**: 기존 SQLite 접근을 repository 인터페이스 뒤로 옮긴다. 동작 변경 없이 구조만 바꾸는 단계이므로 기존 테스트가 그대로 통과해야 한다.
5. **금지어 필터 보강**: §6.2의 7개 항목. 특히 1번(봇 메시지 무시)과 2번(쿨다운)은 독립 테스트가 가능하다.
6. **프로필 카드**: 신규 기능 중 가장 위험하다. 외부 API 의존 + 이미지 렌더링(블로킹) + 에셋 관리가 한꺼번에 걸린다. **가장 얇은 end-to-end 버전을 먼저 만들어라** — `/등록` + 텍스트만 있는 임베드 응답이라도 좋다. 그다음 카드 렌더링을 얹는다.
7. **문서 정합성**: README, `docs/operations.md`, `.env.example`, 권한 목록을 최종 코드와 일치시킨다.

## 9. 검증된 기술 제약

이 값들은 확인된 것이다. 다시 조사하지 말고 그냥 지켜라.

- **인터랙션 3초 ACK.** 3초 안에 응답하지 않으면 사용자에게 실패로 표시된다. 느릴 수 있는 모든 명령(AI, 프로필 카드)은 첫 줄에서 `defer`.
- **채널당 메시지 5개/5초.** 금지어 응답 쿨다운의 근거.
- **이벤트 루프 블로킹.** Pillow, 동기 DB 호출, 동기 HTTP는 전부 루프를 막는다. `loop.slow_callback_duration`을 낮추고 asyncio 디버그 모드로 확인할 것.
- **privileged intent.** 심사 기준은 서버 수가 아니라 앱이 접근 가능한 **유저 수 1만 명**이다. 30명 서버는 무관하고, 셀프호스터도 각자 자기 앱을 만들므로 무관하다. 이 때문에 설계를 바꾸지 마라.
- **길드당 역할 250개 상한.** 파티 역할을 역할로 구현한다면 예산을 확인할 것.
- **채널 이름·주제 변경은 채널당 10분에 2회.** 카운터성 채널 이름 갱신은 불가능하다.
- **전역 REST 한도는 초당 50 요청.** 30명 서버에서는 절대 안 닿는다. 이걸 위한 최적화를 하지 마라.

## 10. 완료 조건 (인수 테스트)

제3자가 확인 가능한 형태다. 전부 통과해야 완료다.

**삭제**
- [ ] 삭제된 기능의 슬래시 명령이 Discord에서 사라진다 (전역 명령 동기화 반영 확인)
- [ ] 삭제된 기능의 코드·테이블·설정 키·의존성이 저장소에 남아 있지 않다 (`grep`으로 검증 가능)
- [ ] `requirements.txt`에 더 이상 쓰이지 않는 패키지가 없다
- [ ] 실데이터가 있는 기존 DB에서 마이그레이션이 동작하고, 삭제되는 데이터의 export 경로가 있다

**저장소 계층**
- [ ] SQLite 접근이 repository 인터페이스 뒤에 있고, 도메인 로직이 `sqlite3`를 직접 import하지 않는다
- [ ] 추상화 전후로 기존 테스트가 동일하게 통과한다

**금지어 필터**
- [ ] 봇이 자기 자신의 박제 메시지에 반응하지 않는다 (무한 루프 없음)
- [ ] 같은 길드에 동일 봇 인스턴스가 둘 있어도 서로를 트리거하지 않는다
- [ ] 금지어를 연속 입력해도 채널 메시지 레이트리밋에 걸리지 않는다
- [ ] 응답 템플릿이 설정 파일에서 변경 가능하다
- [ ] `/설정`으로 길드별 on/off가 가능하다

**프로필 카드**
- [ ] `/등록`이 잘못된 UID를 등록 시점에 거부한다
- [ ] 진열장이 비어 있는 UID에 대해 게임 내 설정 방법을 안내하는 메시지를 반환한다
- [ ] 카드 명령이 3초 안에 ACK되고, 렌더링 중 다른 명령이 지연되지 않는다 (동시 실행으로 확인)
- [ ] 네트워크가 없는 상태로 봇이 정상 기동하고, 해당 명령만 실패한다

**전반**
- [ ] AI 키를 비운 상태로 봇이 정상 기동하고, AI 명령만 비활성된다
- [ ] README의 기능 목록·권한 목록·빠른 시작 절차가 실제 코드와 일치한다
- [ ] 기존 `test/` 스위트가 통과한다. 신규 기능에 대한 테스트가 추가되어 있다
- [ ] 깨끗한 환경에서 README만 보고 처음부터 셋업이 가능하다 (셀프호스터 관점 검증)
- [ ] 하드코딩된 길드/채널/역할 ID가 없다
- [ ] 두 번째 길드에 초대했을 때 길드별 데이터가 섞이지 않는다

## 11. 프로세스 규칙

- **한 번에 큰 리팩터를 하지 마라.** 각 단계는 독립적으로 검증 가능해야 한다.
- **승인 없이 파괴적 스키마 변경 금지.** 사용자의 운영 서버에 실데이터가 있다.
- **`.env.secrets`, `.env.runtime`, `runtime/`을 절대 커밋하지 마라.** `git add -f`도 쓰지 마라. 저장소 README에 명시된 규칙이다.
- 새 런타임 의존성을 추가하려면 먼저 정당화하고 승인받아라 (§4.2).
- §3의 결정을 되돌리려 하지 마라. 이미 검토했다.
- 계획이 §7의 답변으로 무효화되면, 국소적으로 땜질하지 말고 계획을 다시 세워라.
- 작업 중 이 브리프의 전제가 코드와 다르다는 걸 발견하면 **즉시 보고하라.** 브리프는 README 기준으로 작성되었고 코드로 검증되지 않았다.
